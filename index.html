1. Getting Started with Git

This foundational section guides you through installing Git on Windows, setting up your global user identity, initializing local repositories, inspecting project changes, and executing your first snapshot commit.

1.1 Installing Git on Windows

To work with Git on Windows, download and install Git for Windows, which provides the Git Bash terminal environment, command-line tools, and shell integration.

  1. Download the standalone installer from the official site: git-scm.com/download/win.
  2. Run the .exe wizard and keep the default options recommended by the installer.
  3. Key setting: When prompted for line ending conversions, choose Checkout Windows-style, commit Unix-style line endings (core.autocrlf = true) to avoid cross-platform formatting issues.

Verify Installation

Open Git Bash, Command Prompt, or PowerShell and verify the installed version:

git --version

1.2 Setting Up Your Git Workspace

Before creating or committing to any repository, you must set your global author identity. Git attaches this name and email to every commit you generate. 

# Set your global author name
            git config --global user.name "Your Name"

            # Set your global author email (matches your GitHub account)
            git config --global user.email "your.email@example.com"

            # Set default branch name to 'main' for new repositories
            git config --global init.defaultBranch main
Useful Configuration Inspection Commands
# List all active configurations across system, user, and repository levels
            git config --list --show-origin

            # Check a specific configuration key value
            git config user.name

1.3 Initializing a Repository (git init)

To turn an existing local folder into a Git-managed project, initialize it using the git init command. 

# Navigate to your local project directory
            cd C:/path/to/your/Git_Github_Docs

            # Initialize a new Git repository
            git init
What is the .git folder?

Running git init creates a hidden .git/ directory at the root of your folder. It stores all commit histories, branch references, and internal object stores. Never delete or directly modify this folder unless you intend to destroy local tracking history.

1.4 Reviewing File Changes & The Three States

Git tracks files across three primary local states:

  • Working Directory: Files currently being created, edited, or deleted in your folder.
  • Staging Area (Index): A draft space where file changes are organized before committing.
  • Local Repository (.git): Saved history containing finalized snapshot commits.

Check Workspace Status (git status)

Use git status to see untracked, modified, or staged files:

# Full status inspection
            git status

            # Compact status view
            git status -s

Inspect Line Differences (git diff)

Review exact line-by-line modifications made to your files:

# Compare Working Directory changes against the Staging Area
            git diff

            # Compare Staging Area changes against the latest commit
            git diff --staged

1.5 Executing Your First Commit

A commit creates an immutable snapshot of your staged files in the local Git history.

Step 1: Stage Files

# Stage a specific file
            git add index.html

            # Stage all modified and untracked files in the repository
            git add .

Step 2: Commit Staged Files

# Commit staged changes with an informative snapshot message
            git commit -m "Initial commit: Add base layout and Section 1 documentation"
Pro Tip: Shortcut for Tracked Files

To stage modified files and commit them in a single step (skips untracked files): 

git commit -am "Update Section 1 styles and fix markup spacing"

Section 1 Quick Reference

Command Description

git config --global user.email "email" Sets the global author email address associated with your commits.
git init Initializes a new Git repository and creates the hidden .git/ directory.
git status Displays active states of untracked, modified, and staged files.
git diff Shows unstaged line-by-line file changes in the working directory.
git add <file> Moves specified file modifications into the Staging Area (Index).
git commit -m "msg" Saves staged changes as an immutable snapshot in the local repository.

2. Git & GitHub Integration

This section covers linking your local Git environment with GitHub, creating remote repositories, pushing local code, pulling updates, and managing remote authentication seamlessly.

2.1 GitHub Account & Authentication Setup

GitHub acts as a cloud host for Git repositories. To interact with GitHub securely from your terminal without entering passwords repeatedly, set up an SSH Key or a Personal Access Token (PAT).

  1. Sign up for an account at github.com.
  2. Generate an SSH Key pair in Git Bash: 
    ssh-keygen -t ed25519 -C "your.email@example.com"
  3. Start the SSH agent in the background and add your private key: 
    eval "$(ssh-agent -s)"
            ssh-add ~/.ssh/id_ed25519
  4. Copy your public key to your clipboard: 
    clip < ~/.ssh/id_ed25519.pub
  5. Navigate to GitHub Settings > SSH and GPG keys > New SSH key and paste your public key.

Test SSH Connection

ssh -T git@github.com
Expected output: "Hi username! You've successfully authenticated..."

2.2 Connecting & Pushing Local Repo to GitHub

Once you create a new empty repository on GitHub (without initializing a README or .gitignore), link your existing local project to the remote server.

Step 1: Add Remote Origin URL

# Using SSH (Recommended)
            git remote add origin git@github.com:username/Git_Github_Docs.git

            # OR using HTTPS
            git remote add origin https://github.com/username/Git_Github_Docs.git

Step 2: Rename Default Branch & Push Initial Commit

# Ensure local main branch is named 'main'
            git branch -M main

            # Push local commits to remote 'origin' and set upstream tracking (-u)
            git push -u origin main
What does the -u (or --set-upstream) flag do?

The -u flag links your local main branch to the remote origin/main branch. Once linked, you can simply run git push or git pull without specifying the remote name and branch every time.

2.3 Managing Remotes & Tracking Remote Changes

Inspect remote links, update URLs, or remove remote associations as your project evolves. 

# View linked remote repositories with URLs
            git remote -v

            # Show detailed remote tracking info and branch mappings
            git remote show origin

            # Change remote URL (e.g., switching from HTTPS to SSH)
            git remote set-url origin git@github.com:username/Git_Github_Docs.git

2.4 Syncing Remote Changes (git fetch vs git pull)

When changes are made directly on the GitHub website or pushed by collaborators, you must synchronize your local repository with the remote server.

Fetch vs Pull

  • git fetch: Downloads new data and commits from remote without merging them into your working files. Safest for inspecting remote work first.
  • git pull: Downloads remote changes AND automatically attempts to merge them into your current local branch (equivalent to git fetch + git merge).
# Fetch remote metadata without altering local working code
            git fetch origin

            # Inspect differences between local main and remote main after fetching
            git diff main origin/main

            # Pull latest commits and integrate them directly into your active branch
            git pull origin main
Keep local repo clean before pulling

Always run git status before performing a git pull to ensure you don't have uncommitted working directory changes that could lead to unexpected merge conflicts.

git push -u origin <branch> Uploads local commits to GitHub and sets upstream branch tracking.

3. Fork, Clone & History Inspection

This section covers copying remote repositories (forking and cloning), inspecting commit history using logs and filters, viewing file details across time, making changes, and safe techniques for undoing or reverting commits.

3.1 Understanding Forking vs. Cloning

While both operations copy a repository, they serve fundamentally different roles in Git and GitHub workflows:

  • Forking (GitHub feature): Creates a server-side copy of someone else's public GitHub repository under your own GitHub account. It allows you to freely experiment or contribute to open-source projects via Pull Requests without affecting the original project.
  • Cloning (Git feature): Downloads a complete copy of a remote repository (including full history, branches, and commit logs) onto your local computer.

Cloning a Repository

To copy a remote repository to your local computer:

# Clone a repository using SSH
            git clone git@github.com:username/repository-name.git

            # Clone into a custom directory name
            git clone git@github.com:username/repository-name.git my-custom-folder

3.2 Exploring Git Commit Logs

Git records every snapshot made to the project history. The git log command lets you inspect author metadata, dates, commit hashes, and commit messages. 

# Basic commit log history
            git log

            # Display compact history (one line per commit with abbreviated hash)
            git log --oneline

            # View commit history formatted as a visual ASCII graph showing branches
            git log --oneline --graph --all

            # Display last N commits
            git log -n 5

            # Filter commits by author or date range
            git log --author="Your Name"
            git log --since="2 weeks ago"

3.3 Inspecting Commit & File Details

To analyze specific changes made in a past commit or trace line modifications to a file, use git show and git blame.

Inspect Specific Commit Details (git show)

# View changes, author, and timestamp for the HEAD (latest) commit
            git show HEAD

            # View changes introduced in a specific commit hash
            git show 7a1b3f2

Line-by-Line Tracking (git blame)

Identify who modified specific lines in a file and in which commit: 

# Show author and commit hash for every line in index.html
            git blame index.html

            # Inspect line range 10 to 25 only
            git blame -L 10,25 index.html

3.4 Undoing Changes & Reverting Commits

Git provides multiple commands to discard uncommitted working changes, unstage files, or safely reverse pushed commits.

1. Discard Unstaged Working Directory Changes

# Discard local uncommitted changes in a specific file
            git restore index.html

            # Discard all local working changes in current directory
            git restore .

2. Unstage Files from Staging Area

# Move a file out of the staging area back to working directory
            git restore --staged index.html

3. Revert an Existing Commit Safely (git revert)

git revert creates a new commit that inverses the changes of a specified past commit. This is the safest way to undo changes on remote/public branches because it preserves commit history. 

# Revert the latest commit safely
            git revert HEAD

            # Revert a specific historical commit hash
            git revert 7a1b3f2
Reset vs. Revert

git reset --hard <commit> moves the current branch pointer backward, permanently erasing uncommitted changes and commit history. Never use git reset --hard on shared remote branches; use git revert instead.

Section 3 Quick Reference

Command Description
git clone <url> Downloads a complete remote repository and tracking history to local machine.
git log --oneline --graph Displays branch topology and commit history in a compact single-line graph format.
git show <hash> Outputs commit metadata and line diff details for a specific commit hash.
git blame <file> Shows line-by-line author annotations and commit hashes for a file.
git restore <file> Discards unstaged modifications made in the working directory.
git restore --staged <file> Unstages a file while keeping its changes intact in the working directory.
git revert <hash> Creates a new inverse commit to safely undo changes without modifying history.

4. Working with Branches

This section covers branch creation and switching, managing branches on terminal and GitHub, adding .gitignore files, visual branch graphing, local merging, and opening Pull Requests (PRs).

4.1 What is a Branch?

A branch in Git is essentially a lightweight, movable pointer to a specific commit snapshot. Branching enables you to isolate new feature development, bug fixes, or experimental code from the main production codebase (main).

4.2 Branch Management Commands

You can manage branches directly using terminal commands or via the GitHub web interface.

Create & Switch Branches

# List all local branches (* indicates current branch)
            git branch

            # List both local and remote-tracking branches
            git branch -a

            # Create a new branch named 'feature/sidebar'
            git branch feature/sidebar

            # Switch to an existing branch
            git switch feature/sidebar
            # (Legacy alternative: git checkout feature/sidebar)

            # Shortcut: Create and immediately switch to a new branch
            git switch -c feature/sidebar
            # (Legacy alternative: git checkout -b feature/sidebar)

Delete & Rename Branches

# Rename active branch locally
            git branch -m feature/new-sidebar-layout

            # Safely delete a local branch (only if fully merged)
            git branch -d feature/sidebar

            # Force delete an unmerged local branch
            git branch -D feature/sidebar

            # Delete a remote branch from GitHub
            git push origin --delete feature/sidebar

4.3 Preventing Unwanted Files (.gitignore)

A .gitignore text file instructs Git to ignore specific files, patterns, or directories (e.g., build artifacts, sensitive API keys, or dependency folders like node_modules/).

Example .gitignore file content:

# Dependency directories
            node_modules/
            vendor/

            # Environment files containing secrets
            .env
            .env.local

            # Operating System system files
            .DS_Store
            Thumbs.db

            # Log files
            *.log
Important: Ignoring previously tracked files

If a file was already committed, adding it to .gitignore later will not stop Git from tracking it. You must clear it from the index first: 

git rm --cached .env
            git commit -m "Stop tracking .env file"

4.4 Branch Visualization & Merging

Terminal Branch Topology Graphing

# View visual branch split and merge topology
            git log --oneline --graph --all --decorate

Merging Branches Locally

To integrate changes from a feature branch back into your main branch: 

# Step 1: Switch to the receiving target branch
            git switch main

            # Step 2: Ensure main branch is up-to-date with remote
            git pull origin main

            # Step 3: Merge feature branch changes into main
            git merge feature/sidebar

4.5 Pull Requests (PRs) in GitHub

Instead of merging code directly into main on your local terminal, collaborative development relies on Pull Requests on GitHub to review code before merging.

  1. Push your feature branch to GitHub: 
    git push -u origin feature/sidebar
  2. Navigate to your GitHub repository page.
  3. Click the "Compare & pull request" banner.
  4. Provide a descriptive title and summary of changes, then click "Create pull request".
  5. Once reviewed and approved, click "Merge pull request" on GitHub.
  6. Pull the merged changes down to your local machine: 
    git switch main
            git pull origin main

Section 4 Quick Reference

Command Description

git branch -d <branch> Deletes a local branch safely after ensuring it is merged.
git rm --cached <file> Removes a file from Git tracking without deleting it from disk.
git log --graph --oneline Displays an ASCII graph of branch trees and commit histories.
git merge <branch> Integrates changes from the specified branch into the current active branch.
git push origin --delete <branch> Removes a specified branch from the remote GitHub repository.

5. Merge Conflicts & Repository Tags

This section explains why merge conflicts occur, how to resolve them locally in your terminal or editor, how to handle conflicts directly on GitHub, and how to tag release milestones in your Git repository.

5.1 Understanding Merge Conflicts

A merge conflict occurs when Git cannot automatically reconcile differences between two commits. This typically happens when:

  • The same line in a file was modified differently across two branches being merged.
  • A file was edited in one branch but deleted in the other branch.
Git does not overwrite conflicting code automatically

Instead of guessing which change is correct, Git halts the merge operation, inserts conflict markers directly into the affected files, and waits for a human developer to decide which changes to keep.

5.2 Resolving Conflicts on the Terminal & Code Editor

Step 1: Identify Conflicted Files

When a merge fails, check status to list unmerged paths:

git merge feature/new-layout
            # Output: CONFLICT (content): Merge conflict in index.html
            # Automatic merge failed; fix conflicts and then commit the result.

            git status
            # Conflicted files will appear under "Unmerged paths:"

Step 2: Inspect Conflict Markers

Open the conflicted file in your editor (e.g., VS Code). You will see markers separating conflicting sections:

<<<<<<< HEAD (Your Current Branch)
            <h1>Welcome to Git Docs</h1>
            =======
            <h1>Welcome to Git & GitHub Mastery Handbook</h1>
            >>>>>>> feature/new-layout (Incoming Branch)
  • <<<<<<< HEAD: Changes in your currently checked-out branch.
  • =======: The divider between conflicting changes.
  • >>>>>>> branch-name: Incoming changes from the branch being merged.

Step 3: Resolve & Finalize Commit

Edit the file manually to keep the desired code, remove all conflict markers (<<<<<<<, =======, >>>>>>>), and stage the fix:

# Stage the resolved file
            git add index.html

            # Complete the merge commit
            git commit -m "Fix merge conflict in index.html"
Aborting a Merge

If you make a mistake or want to restore your repository to its pre-merge state at any point:

git merge --abort

5.3 Resolving Conflicts on GitHub

If a Pull Request has conflicting changes, GitHub disables the "Merge pull request" button and provides a web-based conflict editor:

  1. Click the "Resolve conflicts" button inside your open Pull Request.
  2. Locate the conflict markers directly in the browser editor interface.
  3. Edit the file to keep the correct lines and remove all marker lines.
  4. Click "Mark as resolved" in the top-right corner.
  5. Click "Commit merge" to update the branch and allow PR merging.

5.4 Adding Tags to Repository Milestones

Tags are reference pointers to specific commits in history, most commonly used to mark release milestones (e.g., v1.0.0, v2.1.0).

Lightweight vs. Annotated Tags

  • Lightweight Tags: Simple pointers to a specific commit hash.
  • Annotated Tags (Recommended): Stored as full checksummed objects with tagger name, email, date, and release message.
# Create an annotated release tag on the current HEAD commit
            git tag -a v1.0.0 -m "Release version 1.0.0: Initial release with full section coverage"

            # Create a tag for a specific past commit hash
            git tag -a v0.9.0 7a1b3f2 -m "Beta preview build"

            # List all tags in the repository
            git tag -l

            # View details and commit metadata associated with a tag
            git show v1.0.0

Pushing Tags to Remote GitHub Server

Standard git push commands do not automatically send tags to remote servers. You must explicitly push them:

# Push a specific tag to GitHub
            git push origin v1.0.0

            # Push all local tags to GitHub at once
            git push origin --tags

            # Delete a tag locally
            git tag -d v1.0.0

            # Delete a remote tag on GitHub
            git push origin --delete v1.0.0

6. Collaboration in GitHub

This section covers team workflows, protecting production branches, enforcing peer review policies in Pull Requests, and efficiently managing project Issues and Discussions on GitHub.

6.1 Protecting Branches on GitHub

In production repositories, preventing direct code pushes to main prevents accidental breaking changes. GitHub Branch Protection Rules enforce workflows that require code checks before merging.

  1. Go to your GitHub repository and click Settings.
  2. In the left sidebar, click Branches under the Code and automation section.
  3. Click Add branch protection rule (or edit an existing one).
  4. In the Branch name pattern field, enter main (or target branch name).
  5. Configure key protection toggles:
    • Require a pull request before merging: Disables direct git push origin main.
    • Require approvals: Set minimum required reviewer approvals (e.g., 1 or 2).
    • Dismiss stale pull request approvals when new commits are pushed: Re-evaluates code when updated.
    • Require status checks to pass before merging: Ensures automated CI/CD pipelines succeed first.
  6. Click Create or Save changes.

6.2 PR Reviews & Peer Feedback Workflows

Pull Request reviews allow collaborators to comment on specific lines of code, request improvements, or approve updates.

PR Review Options for Reviewers

  • Comment: Submits general feedback without explicit approval or rejection.
  • Approve: Authorizes merging the PR into the target branch.
  • Request changes: Blocks PR merging until specified code fixes are addressed.
Linking Issues to Pull Requests Automatically

You can automatically close a GitHub Issue when a PR is merged by referencing keywords in your PR description or commit message: 

# Accepted closing keywords inside PR descriptions:
            Closes #12
            Fixes #45
            Resolves #102

6.3 Managing Project Issues & Board Workflows

GitHub Issues track bugs, feature enhancements, and tasks across your team's workflow.

Key Components of GitHub Issues

  • Labels: Categorize issues using colors and tags (e.g., bug, enhancement, documentation, good first issue).
  • Assignees: Assign specific team members responsible for resolving the task.
  • Milestones: Group related issues and PRs toward specific product goals or sprint deadlines (e.g., v1.0 Release).

6.4 Terminal Commands for Team Collaboration

Commands commonly used when managing remote branches with team members: 

# Fetch remote branches and prune stale tracking references deleted on GitHub
            git fetch --prune

            # Switch to a teammate's remote branch locally
            git checkout --track origin/feature/user-auth

            # Check which branches are merged into current active branch
            git branch --merged

            # Check unmerged active work across branches
            git branch --no-merged

7. Markdown Guide

Markdown is the lightweight markup language used across GitHub for formatting README.md files, Pull Request descriptions, issue comments, and documentation sites.

7.1 Text Formatting & Headings

Format text styles using standard Markdown syntax delimiters: 

# Heading Level 1
            ## Heading Level 2
            ### Heading Level 3
            #### Heading Level 4

            **Bold Text** or __Bold Text__
            *Italic Text* or _Italic Text_
            ***Bold and Italic Text***
            ~~Strikethrough Text~~
            `Inline Code Snippet`

7.2 Lists & Interactive Task Lists

Create ordered, unordered, or interactive checkbox lists: 


            * Item A
            * Item B
            * Sub-item B1
            * Sub-item B2

            
            1. First step
            2. Second step
            3. Third step

            
            - [x] Complete Section 6 documentation
            - [ ] Add Section 7 Markdown guide
            - [ ] Add Section 8 GitHub Pages guide

7.3 Links, Images & Media

Embed hyperlinks, remote or repository images, and media assets: 


            [Visit GitHub official site](https://github.com)

            
            [Read License](./LICENSE)

            
            ![Git Architecture Diagram](./assets/images/git-diagram.png "Git Architecture")

            
            <img src="./assets/images/logo.png" alt="Logo" width="200" />

7.4 Tables & Fenced Code Blocks

Markdown Tables

| Command | Description | Level |
            | :--- | :---: | ---: |
            | `git init` | Initialize repo | Basic |
            | `git rebase` | Reapply commits | Advanced |

```bash
            # Language identifier specifies syntax highlighting

            ```

7.5 GitHub Flavored Markdown (GFM) Special Callouts

GitHub supports custom alert boxes in README.md files using standard syntax quotes: 

> [!NOTE]
            > Highlights useful information that users should know.

            > [!TIP]
            > Helpful advice for doing things better or faster.

            > [!IMPORTANT]
            > Crucial information needed for user success.

            > [!WARNING]
            > Critical content demanding immediate user attention to prevent errors.

8. GitHub Pages Deployment

GitHub Pages is a free static web hosting service provided by GitHub that takes HTML, CSS, JavaScript, and asset files directly from a repository and publishes a live website.

8.1 What is GitHub Pages?

GitHub Pages hosts public static websites directly under the github.io domain. It automatically builds and serves code pushed to designated deployment branches (like main or gh-pages) or via GitHub Actions.

URL Structure

  • User / Organization Site: https://<username>.github.io (from repo named <username>.github.io)
  • Project Site: https://<username>.github.io/<repository-name>/ (e.g., https://username.github.io/Git_Github_Docs/)

8.2 Deploying Your Site Step-by-Step

To publish your newly created Git_Github_Docs project using GitHub Pages:

  1. Ensure all local project files (index.html, assets/) are committed and pushed to GitHub: 
    git add .
            git commit -m "Add all 8 documentation sections"
            git push origin main
  2. Navigate to your repository page on GitHub.
  3. Click the Settings tab at the top of the repository.
  4. In the left sidebar menu, click Pages under the Code and automation section.
  5. Under Build and deployment > Source, select Deploy from a branch.
  6. Under Branch, select main branch and / (root) folder from the dropdowns.
  7. Click Save.
Deployment Status & Verification

GitHub will initiate a build workflow. Refresh the Pages settings page after 1–2 minutes until you see a banner stating:
Your site is live at https://username.github.io/Git_Github_Docs/

8.3 Configuring Custom Domains & HTTPS

You can map a custom domain (e.g., gitdocs.yourdomain.com) to your GitHub Pages site:

  • In Settings > Pages, enter your custom domain under Custom domain and click Save.
  • GitHub automatically generates a CNAME file at the root of your repository.
  • In your DNS provider (e.g., Cloudflare, Namecheap, GoDaddy), add a CNAME record pointing your subdomain to username.github.io.
  • Check Enforce HTTPS to ensure secure TLS/SSL traffic.

8.4 Troubleshooting Pages Deployments

404 Page Not Found?
  • Ensure your main entry file is strictly named lowercase index.html located in the repository root directory.
  • Verify that asset paths (e.g., assets/css/style.css) use relative URLs rather than absolute root paths (/assets/...).
